# Schema and Object Map

This page shows how the user-facing `cogni` commands connect to Cognityx
lifecycle objects, generated document artifacts, canonical document structure,
Source Graph, provenance addresses, and the DataForge handoff.

Use this page for orientation and exact public names. Follow the links in each
section for validation rules, persistence details, and Python examples.

## Where Ingest Fits

```text
original file
  -> SourceAsset registration
  -> parser execution and retained native output
  -> compatibility and canonical document artifacts
  -> Source Graph and provenance addresses
  -> DataForge source references
```

Ingest owns source registration, parser results, document structure, provenance,
and the logical lifecycle of those records. Cognityx Storage owns physical
objects and safe byte deletion. Cognityx Jobs owns durable job state and ordered
events. The Python SDK and `cogni` command line are entry points into those
component-owned operations.

## Command Tree

The normal command is `cogni ingest <path>`. The complete current command shape
around Ingest is:

```text
cogni
|-- asset
|   |-- add | list | show | locate | delete | deleted
|-- bundle
|   |-- create | list | locate | delete | deleted
|-- ingest <path>
|-- ingest --asset <asset-id>
|-- ingest --bundle <bundle-path>
|-- ingest-config
|   |-- show | validate
|-- job
|   |-- list | status | show | events | watch | cancel
|-- run
|   |-- list | show | locate | delete
|-- document
|   |-- list | show | locate | delete
|-- artifact
|   |-- available | read | locate
|-- provenance
|   |-- resolve
|-- cleanup
|   |-- blobs
|-- describe
```

Plural command aliases and ID-only `cogni ingest --bundle-id` remain deprecated
compatibility forms. `--storage-root` is also compatibility-only; normal use
loads Cognityx Storage configuration. See the [SDK command guide](/sdk/cli/) for
arguments and examples.

## Lifecycle Objects And Owners

```text
source file
  -> SourceAsset ----> optional DocBundle grouping
  -> IngestRun
     |-- Job (progress, cancellation, audit)
     |-- Document(s)
         |-- generated artifacts
```

| Object | What it means | Owner |
| --- | --- | --- |
| `ResourceContext` | Stable tenant, project, workspace, and principal scope | Cognityx Resource |
| `ExecutionContext` | One operation inside that stable scope | Cognityx Resource |
| `DocBundle` | A named logical collection of source assets | Ingest |
| `SourceAsset` | One registered original file with stable identity and SHA-256 | Ingest metadata; Storage bytes |
| `IngestRun` | One submitted ingest operation and its result references | Ingest |
| Job and events | Durable state, cancellation, and replayable progress | Cognityx Jobs |
| Canonical document | Backward-compatible pages, blocks, sections, objects, and relations | Ingest |
| Canonical content | Parser-neutral v3.2 source model | Ingest |
| Source Graph | Immutable text-free structural and provenance graph revision | Ingest |
| Provenance address | A durable request to resolve exact or logical evidence | Ingest |
| Physical Blob or object | Original or generated bytes behind a logical URI | Cognityx Storage |
| Q/A, claim, or Knowledge Unit | Meaning derived downstream from verified evidence | DataForge |

An ID is the public handle. A `storage://` URI is the public location. A local
filesystem path is an operator detail and is not part of the cross-component
contract. See [Source Assets](sources.md) and the [output contract](contract.md).

## Nine Public Document Artifacts

Artifact commands accept exactly these nine names. The vocabulary is closed:
aliases, filenames, internal underscore names, and arbitrary paths are rejected.

| Public name | Stored file | Kind and main consumer | Source text | Presence |
| --- | --- | --- | --- | --- |
| `document` | `document.json` | v2 compatibility structure for existing document consumers | Yes, in compatibility blocks/objects | Every successful document |
| `evidence` | `evidence.jsonl` | v2 compatibility evidence rows for audit and existing DataForge readers | Yes, in evidence values | Every successful document |
| `provenance` | `provenance.json` | v2 compatibility provenance package and stable handoff for existing DataForge readers | May include compatibility evidence text | Every successful document |
| `manifest` | `manifest.json` | Current authoritative artifact index for SDK and automation | No, references only | Every successful document |
| `canonical-content` | `canonical-content.json` | Current v3.2 parser-neutral source model for segmentation, provenance, and DataForge | Yes, only at `content_nodes[*].content.text` | Every successful document |
| `source-graph` | `source-graph.json` | Current deterministic source/provenance graph for resolution and DataForge | No, canonical IDs and facts only | Every successful document |
| `provenance-addresses` | `provenance-addresses.json` | Current stable evidence addresses for resolver and DataForge | No, targets and selectors only | Every successful document |
| `parser-observations` | `parser/observations.json` | Audit input containing separate parser facts for alignment/fusion | May contain parser-observed values | Conditional: compare/fusion paths that produce observations |
| `parser-fusion-decisions` | `parser/fusion-decisions.json` | Audit output containing replayable adjudication policies and decisions | References observation facts and hashes rather than owning canonical text | Conditional: paths that produce fusion decisions |

`cogni artifact available <document-id>` lists the names present for one
document. `read` returns authorized bytes; `locate` returns safe logical metadata
without exposing a local path. The manifest URI is checked against the configured
Storage URI before use, and byte reads cross Ingest's artifact-specific
authorization boundary.

The exact parser-native payload is separately retained and described; it is not
one of the nine short names. See [Native Parser Artifacts](native-parser-artifacts.md).

## Canonical Content Collections

`canonical-content.json` has `schema`, `document_id`, and these exact top-level
collections:

```text
CanonicalContentArtifact
|-- schema
|-- document_id
|-- resources[]
|-- presentation_units[]
|-- divisions[]
|-- content_nodes[]
|-- representations[]
|-- native_bindings[]
|-- relations[]
|-- processing_activities[]
|-- artifact_descriptors[]
```

| Collection | Important fields | Role |
| --- | --- | --- |
| `resources` | `resource_id`, `source_asset_id`, `source_sha256`, `media_type`, `logical_uri` | Identifies immutable source bytes without embedding them |
| `presentation_units` | `presentation_unit_id`, `unit_type`, `sequence_number`, `physical_index`, typed `labels`, dimensions | Says where content appeared, such as a page or slide |
| `divisions` | `division_id`, `division_role`, parent/child IDs, `title_node_id`, `direct_node_ids`, `sequence_number` | Says how content is organized, such as a section or clause |
| `content_nodes` | `node_id`, `owner_division_id`, `node_kind`, `content`, `source_selectors`, `sequence_number`, `fact_sources` | Owns each exact text occurrence and its support |
| `representations` | `representation_id`, `subject_id`, `representation_type`, `media_type`, artifact/caption/selector IDs | References images, tables, and other forms without copying their content |
| `native_bindings` | `binding_id`, `canonical_id`, `artifact_id`, `native_pointer`, `binding_role` | Connects a canonical record to retained parser-native evidence |
| `relations` | `relation_id`, source/target IDs, `relation_type`, `status`, `epistemic_state`, evidence node IDs | Preserves resolved and uncertain structural relationships |
| `processing_activities` | activity/run/correlation IDs, `method`, parser IDs, input/output artifact IDs | Records compact processing lineage |
| `artifact_descriptors` | `artifact_id`, `role`, `uri`, `media_type`, optional hash/schema | Refers to supporting bytes without duplicating them |

`content_nodes[*].content.text` is the only place this v3.2 artifact stores
extracted source text. Its sibling `sha256` hashes the exact UTF-8 value.
Selectors locate text through source paths, character ranges, page identities,
geometry, or source anchors. Segmentation records contain node IDs and optional
ranges, never copied source text. See [Canonical Content](canonical-content.md)
and [Non-Copying Segmentation Views](non-copying-segmentation-views.md).

`CanonicalText` is the nested `content` pair of exact `text` and its UTF-8
`sha256`. A `CanonicalResource` answers which immutable source the model belongs
to. A `PresentationUnit` answers where content appeared. A `Division` supplies
logical hierarchy, and a `ContentNode` owns one text-bearing occurrence.

A `SourceSelector` locates that occurrence without quoting it again. A
`Representation` describes a non-text or alternate form. A `NativeBinding`
points back to an exact retained parser object. A `CanonicalRelation` records an
auditable edge between canonical records. A `ProcessingActivity` records compact
lineage, while a `CanonicalArtifactDescriptor` refers to independently stored
bytes without copying them.

## Presentation And Logical Structure

These are two different questions:

```text
PresentationUnit: Where did it appear?       page 3, slide 8, sheet 2
Division:         How is it organized?       section 4.2, clause, appendix
ContentNode:      What exact occurrence?     text plus source selectors

Page 3 ---------+
                 +-- Section 4.2
Page 4 ---------+
```

A node belongs directly to exactly one deepest division. Parent divisions point
to child divisions and direct node IDs; they do not store copied subtree text.
Callers reconstruct a subtree by following existing references in canonical
order. A section may span pages, and a page may contain several sections, so
presentation and logical hierarchy must never be treated as the same tree.

## Source Graph

The Source Graph is a compact, immutable map of source structure and provenance.
It projects resources, presentation units, divisions, relations, content nodes,
selectors, representations, native bindings, processing activities, and artifact
descriptors from validated canonical content. It deliberately contains no
canonical source text.

```text
Canonical Content
|-- resources, presentation units, and divisions
|-- content node IDs and selectors
|-- representations and native bindings
|-- explicit relations and processing lineage
|-- artifact descriptors
     -> Source Graph
        |-- content-derived graph_revision
        |-- provenance address catalog
```

The `graph_revision` is content-bound: production validation recomputes the
deterministic fact projection and rejects a revision that does not match. Graph
relations retain `status`, `epistemic_state`, and `gold_eligible`. Ambiguous,
unresolved, contradicted, and rejected relations are never gold support.

This is a source and provenance graph, not a semantic knowledge graph. Entity
extraction, inferred domain relationships, retrieval indexes, and graph database
projections remain downstream work. See [Source Graph And Provenance
Addresses](source-graph-and-provenance-addresses.md).

## Provenance Addresses

A provenance address is a stable evidence request rather than copied evidence.
Three forms are persisted:

- A strong address binds one source SHA-256, graph revision, resource, target,
  and optional selectors. It never redirects.
- A logical address names a resource family, explicit version rule, and division
  reference. It may select one permitted version.
- An evidence-set address binds ordered claim IDs to ordered strong-address
  members. Every required member must resolve exactly for the set to be exact.

`cogni provenance resolve <document-id> <address-id>` returns exactly one of six
closed outcomes:

| Outcome | Meaning |
| --- | --- |
| `exact` | The immutable target, or every evidence-set member, matched |
| `redirected` | A logical address selected one explicitly permitted version |
| `ambiguous` | Several valid candidates remain; none is accepted |
| `obsolete` | The requested address, revision, resource, or version is superseded |
| `forbidden` | The target exists but policy denied access; protected details are omitted |
| `unresolved` | The requested address or required member cannot be resolved |

Resolution is deterministic and read-only. It does not initialize inference,
open parser-native payloads, fabricate evidence, or turn a candidate into gold
support.

## DataForge Handoff

Each successful document with the current provenance artifacts contributes one `dataforge_source_refs`
entry to the run manifest. The entry is a packing list of exact stored objects,
not a copy of their content. It contains exactly:

```text
Ingest artifacts
  -> run manifest dataforge_source_refs
     -> DataForge
        |-- paragraph Q/A
        |-- composite Knowledge Units
```

```text
document_id
provenance_uri
canonical_content_uri
source_graph_uri
provenance_addresses_uri
```

Every location is a logical `storage://` URI. The canonical, graph, and address
values exactly match that document's `provenance.json` `artifact_uris`. Failed
documents receive no placeholder entry. Existing `document_manifest_refs`,
`evidence_refs`, and `provenance_refs` retain their meanings.

DataForge validates the Source Graph and address result before using support.
Only an `exact` ordered closure can be gold support. DataForge owns generated
paragraph Q/A, claims, composite Knowledge Units, and later semantic processing.

## Delete And Cleanup Map

Deletion is intentionally split between logical records and physical bytes:

| Operation | What changes | What remains |
| --- | --- | --- |
| `asset delete --yes` | Soft-deletes one SourceAsset record | Shared Blob and dependent generated records |
| `bundle delete --yes` | Soft-deletes a bundle; `--recursive` is required for live descendants | Previously generated runs/documents and shared Blobs |
| `run delete --yes` | Removes that run's generated metadata tree | Documents, SourceAssets, and durable job history |
| `document delete --yes` | Removes that document's generated storage tree | SourceAsset Blob and durable job history |
| Job | Has no delete command; lifecycle and audit history are retained | Job state and ordered events |
| Individual artifact | Has no arbitrary public delete command | Artifact lifecycle follows its owning document/policy |
| `cleanup blobs` | Produces a dry-run Storage cleanup plan | All bytes remain |
| `cleanup blobs --yes` | Executes a fresh reference-checked Storage plan | Any referenced, too-new, or otherwise protected Blob |

Cleanup is explicit today; it is not an always-running background service.
Storage rechecks live references, content-addressed identity, age, and metadata
before physical deletion. Parser-extraction retention and purge have an additional
policy boundary: expiry never overrides an active reference or legal hold, and
Ingest records purge only after Storage reports the payload absent. See
[Extraction Reuse, Retention, And Purge](extraction-reuse-retention-purge.md).
